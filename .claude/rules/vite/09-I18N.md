# I18N.md — Internationalization (use-intl + React Router)

Skip this file entirely if the project has no i18n.

**Why use-intl:** it is the framework-agnostic core of next-intl. Same `useTranslations`, same
ICU message syntax, same JSON files, same namespaces — a component is written identically in a
Next project and a Vite project. Only the plumbing (loading, routing) differs.

---

## Install

```bash
npm install use-intl
```

---

## File Structure

```
src/locales/           ← ALWAYS "locales/", NEVER "messages/"
  es/common.json, home.json, [page].json
  en/common.json, home.json, [page].json

src/config/i18n.config.ts   ← locales, defaultLocale, Locale type, routeTranslations
src/i18n/messages.ts        ← loadMessages(locale): merges one locale's files, single source of truth
src/i18n/paths.ts           ← localizedPath(routeKey, locale) — the only URL builder
src/hooks/useLocaleData.ts  ← current locale + messages, read from the matched route
src/hooks/useChangeLanguage.ts
```

## i18n/messages.ts — Namespace Convention

Files are discovered with `import.meta.glob`: adding a page means adding its JSON, nothing
else. Each file is its own chunk, so only the ACTIVE locale (plus the default, as the fallback
layer) is ever downloaded.

```ts
// common.json spreads at root. Each other file namespaces under its file name.
const files = import.meta.glob<{ default: Record<string, unknown> }>("@/locales/*/*.json")

const loadLocale = async (locale: Locale) => {
  const own = Object.entries(files).filter(([path]) => path.includes(`/locales/${locale}/`))
  const loaded = await Promise.all(own.map(async ([path, load]) => [fileKey(path), (await load()).default] as const))
  const { common, ...pages } = Object.fromEntries(loaded)
  return { ...common, ...pages }   // nav, footer, actions, errors at root; home, about… namespaced
}

export const loadMessages = async (locale: Locale) =>
  locale === defaultLocale
    ? loadLocale(locale)
    : deepMerge(await loadLocale(defaultLocale), await loadLocale(locale))   // fallback layer
```

`fileKey("/src/locales/es/about.json")` → `"about"`. `deepMerge` lives in `src/utils/`.

## Component Pattern — Every Component Owns Its Translations

```tsx
// ✅ Each section calls useTranslations directly
import { useTranslations } from 'use-intl'
export function HomeHero() {
  const t = useTranslations('home.hero')
  return <h1>{t('title')}</h1>
}

// ✅ Page controller renders sections with ZERO content props
export function HomePage() {
  return <><HomeHero /><HomeSoluciones /><HomeStats /></>
}

// ❌ Never pass translation strings as props to section components
<HomeHero title={t('hero.title')} />   // BANNED
```

Exception: truly shared layout primitives (FAQAccordion, etc.) may receive translated strings as props, since they can't know their namespace.

## Namespace Pattern

```
useTranslations('nav')             ← common.json nav key
useTranslations('footer')          ← common.json footer key
useTranslations('home.hero')       ← home.json hero key
useTranslations('about.faq')       ← about.json faq key
```

Always: `useTranslations('[page].[section]')`.

## Constants vs Locales Architecture

**src/constants/*.ts** — keys, hrefs, structure, pure data. Never translated text.
**src/locales/**/*.json** — translated strings only.

```
Nav links: constants hold { labelKey, routeKey }, locale JSON holds string for labelKey
FAQs: constants hold key list, locale JSON holds question/answer text
Phone numbers, emails, coordinates → constants, not locales
```

## Type-safe keys — a wrong key is a `tsc` error

Declare the messages type once, from the DEFAULT locale's files:

```ts
// src/i18n/types.d.ts
import type { Locale } from "@/config/i18n.config"
type Messages =
  typeof import("@/locales/es/common.json") & {
    home: typeof import("@/locales/es/home.json")
    about: typeof import("@/locales/es/about.json")
  }
declare module "use-intl" {
  interface AppConfig { Locale: Locale; Messages: Messages }
}
```

`t("hero.titel")` and `useTranslations("abuot")` now fail the build instead of printing the key
on screen. A page left out of this type cannot be translated at all (its namespace does not
exist), so the error itself reminds you to add it.

## Dates, numbers, plurals — always through the library

```tsx
// ❌ BANNED
date.toLocaleDateString()          // follows the device, not the page language
`${count} items`                   // wrong in every language with other plural rules
price.toFixed(2) + " €"

// ✅
const format = useFormatter()
format.dateTime(date, { dateStyle: "long" })
format.number(price, { style: "currency", currency: "EUR" })
t("items", { count })              // "items": "{count, plural, one {# plato} other {# platos}}"
```

---

## Missing keys at runtime — never a raw key on screen

- **The default locale is the fallback layer.** Messages are the default locale's messages with
  the active locale merged on top (deep merge), so a key missing in one language shows the
  default-language text, never `home.hero.title`.
- `onError` → `logger.error` (never the console default, never a throw in production).
- `getMessageFallback` → for a key missing everywhere, return `""` in production and the key
  path in development, so it is visible while building and invisible to visitors.
- Both are props of `<IntlProvider>` in `RootLayout`.

## Translated Slugs — one route per locale, generated

There is no server and no proxy, so translated slugs are real routes. They are **generated**
from one table — never written by hand per language, never physical folders per slug.

```ts
// src/config/i18n.config.ts
export const locales = ["es", "en"] as const
export type Locale = (typeof locales)[number]
export const defaultLocale: Locale = "es"

// routeKey → slug per locale. "" = the locale's home.
export const routeTranslations = {
  home:  { es: "",               en: "" },
  about: { es: "sobre-nosotros", en: "about" },
} as const satisfies Record<string, Record<Locale, string>>
export type RouteKey = keyof typeof routeTranslations
```

```ts
// src/i18n/paths.ts — default locale unprefixed ("as-needed"), others prefixed
export const localizedPath = (routeKey: RouteKey, locale: Locale): string => {
  const prefix = locale === defaultLocale ? "" : `/${locale}`
  const slug = routeTranslations[routeKey][locale]
  return `${prefix}/${slug}`.replace(/\/+$/, "") || "/"
}
```

```tsx
// src/app/router.tsx — i18n projects build the locale branches like this
export const router = createBrowserRouter([
  {
    element: <RootLayout />,            // pathless: stays mounted across a language switch
    children: locales.map((locale) => ({
      id: `locale-${locale}`,
      path: locale === defaultLocale ? "/" : `/${locale}`,
      loader: () => loadMessages(locale),
      handle: { locale },
      children: [{
        errorElement: <RouteError />,
        children: [
          { index: true, element: <HomePage />, handle: { routeKey: "home" } },
          { path: routeTranslations.about[locale], handle: { routeKey: "about" },
            lazy: page(routeModules.about, "AboutPage") },
          { path: "*", lazy: page(routeModules.notFound, "NotFoundPage") },
        ],
      }],
    })),
  },
])
```

- Every page route carries `handle: { routeKey }` — that is how the language switcher finds
  the same page in the other language.
- `RootLayout` is pathless and ABOVE the locale branches, so switching language does not
  remount Providers, the loader, Lenis or the navbar.
- `routeModules` and `preloadRoute` are keyed by **routeKey**, not by path (06-TRANSITIONS.md):
  `preloadRoute` resolves the href to its routeKey first.
- Every internal link is built with `localizedPath(routeKey, locale)` — never a hardcoded
  string, never a slug in the default language used for every locale.

## RootLayout — the IntlProvider

```tsx
// src/hooks/useLocaleData.ts — locale + messages from the matched locale route
export const useLocaleData = () => {
  const match = useMatches().find((m) => isLocaleHandle(m.handle))
  const locale = (match?.handle as { locale: Locale } | undefined)?.locale ?? defaultLocale
  const messages = useRouteLoaderData(`locale-${locale}`) as Messages
  return { locale, messages }
}

// src/components/layout/RootLayout.tsx
const { locale, messages } = useLocaleData()
<IntlProvider locale={locale} messages={messages} timeZone={appConfig.timeZone}>
  <Providers>…</Providers>
</IntlProvider>
```

- The current locale comes from the **matched route**, then `useLocale()` inside the provider.
  Never parse `location.pathname` with a regex to find it.
- `RootLayout` also sets `document.documentElement.lang = locale` in an effect
  (08-ACCESSIBILITY.md).
- Pass `timeZone` explicitly: without it, dates format in the visitor's zone and differ
  between devices.

## useChangeLanguage — the language switch

```ts
export const useChangeLanguage = () => {
  const current = useLocale() as Locale
  const routeKey = useCurrentRouteKey()          // from the matched route's handle
  const { navigateTo } = useTransition()

  return (lang: Locale) => {
    if (lang === current) return
    try { localStorage.setItem("preferred-language", lang) } catch {}
    navigateTo(localizedPath(routeKey ?? "home", lang))
  }
}
```

- **Navigate**, never `window.history.replaceState()`: swapping the URL does not change the
  matched route, so the messages never change.
- No `NEXT_LOCALE` cookie: it only existed for Next's middleware. The URL is the source of
  truth; `localStorage` only remembers the choice.
- Same page in the other language (via `routeKey`), never back to the home page.

### First visit

- A deep link always opens in the language of its URL — a shared `/en/about` stays English.
- Only on the bare default-locale home (`/`), with no stored preference: if
  `navigator.languages` prefers another supported locale, redirect there once and store it.
  A stored preference wins over the browser language. Never redirect any other URL.

## Physical Folder Structure

No folder per locale and no file per translated slug. One page component per `routeKey`,
in `src/components/pages/[page]/`. The router generates the per-locale paths.
